# Project Context: «ProjectA»

## Документация и Концепт
* **Актуальный GDD:** [Google Docs Link](https://docs.google.com/document/d/1LBGFN0nu7oEQ_cPvqBS0dRfp8DaXYPq7sDYE6lrgYBM/)
* **Документация PurrNet:** Локальная копия в `PurrDocs-main/` ([онлайн](https://purrnet.dev/docs))
* **Кратко об игре:** Кооперативно-соревновательный физический 3D-платформер. Игроки проходят трассу, мешая или помогая друг другу. Инвентаря нет: игроки сканируют эталонные предметы на уровне и **сами превращаются в эти физические объекты** (мост, батут, наковальня и т.д.). Эталонный предмет уничтожается после первого успешного сканирования (один игрок на предмет; при одновременном сканировании побеждает тот, чей `ServerRpc` дошёл первым).

## Технический стек
* **Движок:** Unity 6 (HDRP 17.x).
* **Язык:** C#.
* **Сетевой фреймворк:** [PurrNet](https://purrnet.dev/docs) (архитектура Host/Client, в будущем через Steam Transport).
* **CSP-модуль:** PurrDiction (аддон PurrNet для Client-Side Prediction).
* **Тестирование:** ParrelSync (для запуска нескольких экземпляров редактора).

## Графика и ассеты
* **Стадия:** Только примитивы (Cube, Sphere, Capsule, Cylinder). Графика, модели и финальные ассеты будут добавлены **после** завершения программной части.
* **ИИ не должен** предлагать подключать ассеты, текстуры, шейдеры или сторонние модели. Все формы, уровни и механизмы собираются из примитивов с базовыми цветными материалами.
* **Подготовка к замене:** Чтобы переход на финальные ассеты был безболезненным, соблюдать правила:
  - **Разделять логику и визуал.** Скрипты не должны зависеть от конкретного меша или иерархии визуальных объектов. Визуальная модель — child-объект (например, `Graphics/`), на который логика ссылается через `[SerializeField]` или `Transform` ссылку, а не через `GetComponent` по жёстким путям.
  - **Коллайдеры — отдельно от меша.** Использовать простые коллайдеры (Box, Sphere, Capsule) на объекте с логикой, а не MeshCollider на визуале. При замене меша коллайдеры остаются на месте (возможно, потребуется подгонка размеров).
  - **Данные формы — в ScriptableObject.** `FormData` (ID, допустимые слоты, масса, PhysicsMaterial, размер коллайдера, префаб визуала) хранятся в SO. При замене достаточно обновить поле «префаб визуала» в SO, не трогая код.
  - **Не хардкодить размеры.** Габариты и offsets брать из ScriptableObject или компонентов, не вписывать magic numbers в код.

## КРИТИЧЕСКИЕ ПРАВИЛА СЕТЕВОЙ РАЗРАБОТКИ (ДЛЯ ИИ)

Любой генерируемый код **должен** учитывать мультиплеерную специфику с первой строчки. Код, написанный только для синглплеера, будет отклонен.

### Базовый класс
* Все скрипты, участвующие в сетевом взаимодействии, наследуются от `NetworkBehaviour` (который сам наследует `NetworkIdentity`), **не** от `MonoBehaviour`.
* `NetworkBehaviour` предоставляет: `isServer`, `isOwner`, `IsController`, `owner`, `ServerRpc`, `ObserversRpc`, `TargetRpc`, `SyncVar` и другие sync-типы.

### 1. Ввод и контроль (Authority)
* **Архитектура — Host/Client:** Выделенного сервера нет. Один из игроков является хостом (и сервер, и клиент одновременно). `isServer == true` только на хосте.
* Считывание инпута (клавиатура/мышь) происходит **только** если `IsController == true`.
  - `IsController` возвращает `true` в двух случаях:
    - У объекта **есть владелец** (owner) и **мы — этот владелец** (наш `PlayerID` совпадает).
    - У объекта **нет владельца** и **мы — хост** (т.к. хост выполняет серверную роль).
  - Пример: объект-машина без владельца → `IsController == true` только на хосте. Персонаж игрока с owner → `IsController == true` только у этого игрока.
* Если `IsController == false`, контроллер **не реагирует на инпут**. Положение и повороты приходят по сети через `NetworkTransform` или `NetworkRigidbody` с интерполяцией.

### 2. Синхронизация движения — двухфазная стратегия

**Этап 1 (MVP):** Owner-Auth `NetworkRigidbody` / `NetworkTransform`.
* Владеющий клиент применяет физику/движение локально; `NetworkRigidbody` (Owner Auth = true) синхронизирует `Rigidbody`-состояние остальным через spring-based интерполяцию.
* Для `CharacterController` используется `NetworkTransform` (Owner Auth = true) с включённым `Character Controller Patch`.
* Сервер **не** симулирует физику движения — авторитет у владельца. Это responsive, но менее competitive.
* Геймплейно-критичные действия (сканирование, трансформация, урон) всё равно проходят через `ServerRpc`.

**Этап 2 (после MVP):** PurrDiction (Client-Side Prediction).
* Миграция контроллера на `PredictedIdentity<INPUT, STATE>`. Важно: этот класс наследуется от `MonoBehaviour`, а не `NetworkBehaviour`.
* Сервер становится авторитетной симуляцией; клиенты предсказывают и получают reconciliation.
* State Machine персонажа мигрирует на `PredictedStateMachine` + `PredictedStateNode`. 
  - **Критично для стейтов:** В `PredictedStateNode` метод `Simulate(...)` должен быть пустым (`{ }`), а вся логика состояния пишется строго в `StateSimulate(in TInput input, ref TState state, float delta)`. Иначе логика будет выполняться каждый сетевой тик даже для неактивных состояний!
* **Чтение инпута:**
  - Инпут читается строго в `UpdateInput(ref TInput input)`. 
  - **Запрещено** читать локальный инпут напрямую внутри `StateSimulate` или `Simulate`. Все данные управления должны передаваться через структуру `TInput`. Если прочитать инпут напрямую в `Simulate`, на сервере он будет равен нулю, что вызовет жесткий rubberbanding клиента.
* **Жизненный цикл:** Вместо `Start()` или `OnSpawned()`, инициализация логики, зависящей от владельца (включение инпута, привязка камеры), должна происходить в `protected override void SimulationStart()`, так как к этому моменту `isOwner` гарантированно назначен.
* **Визуал и интерполяция:** Визуальные модели/примитивы не должны крепиться к физическому корню (`transform`), так как он двигается рывками по тикам. Они должны крепиться к объекту, указанному в `PredictedTransform.Graphics` (или быть дочерними для папки визуала), чтобы PurrDiction плавно их интерполировал.
* INPUT и STATE — `struct : IPredictedData`. Все мутабельные значения (позиция, скорость, кулдауны, ID скопированных форм) хранятся в STATE.
* Серверная валидация — через `SanitizeInput(ref INPUT)` + проверки в `Simulate`.

### 3. RPC вместо локальных вызовов
* Смена важных состояний (сканирование предмета, трансформация, использование способности) **не выполняется локально**.
* **Паттерн:**
  1. Клиент вызывает `[ServerRpc]` → 
  2. Сервер проверяет валидность (существует ли предмет, легальна ли трансформация, не истёк ли кулдаун) → 
  3. Сервер вызывает `[ObserversRpc]` или обновляет `SyncVar` → 
  4. Все клиенты синхронно обновляют визуальное и физическое состояние.
* Для получения информации об отправителе RPC используется `RPCInfo info = default` как последний параметр.

### 4. Инстанцирование и уничтожение объектов
* PurrNet автоматически сетеёт `Instantiate`/`Destroy` для объектов с `NetworkIdentity`.
* Однако право на спавн/деспавн регулируется **Network Rules**. По умолчанию (Server Auth) — только сервер может создавать/удалять.
* Для передачи данных вместе со спавном используются `OnSerialize`/`OnDeserialize` (данные приходят до `OnSpawned`).

### 5. Sync-типы для состояния
* `SyncVar<T>` — для простых значений (HP, текущее состояние, ID формы).
* `SyncList<T>` — для коллекций (список скопированных форм).
* По умолчанию sync-типы — **Server Auth** (`ownerAuth: false`). Для значений, контролируемых владельцем, явно указывать `ownerAuth: true`.

### 6. Архитектурная шпаргалка: CSP vs ServerRpc vs SyncVar
* **КРИТИЧЕСКОЕ ПРАВИЛО:** `PredictedIdentity` **НЕ ЯВЛЯЕТСЯ** наследником `NetworkIdentity` или `NetworkBehaviour`! Это полностью изолированная параллельная система предсказаний, унаследованная от `MonoBehaviour`. 
  - Вы **НЕ МОЖЕТЕ** использовать `[ServerRpc]`, `[ObserversRpc]` или `SyncVar` внутри `PredictedIdentity` или `PredictedStateNode`.
  - Если вам нужен `SyncVar` или RPC на предсказываемом объекте, вам придется создавать отдельный скрипт-наследник `NetworkBehaviour`, вешать на префаб `NetworkIdentity` и связывать их, ЛИБО решать задачу чисто средствами CSP (`IPredictedData` / `hierarchy.Delete`).
  - **Всегда проверяйте исходники фреймворка** (через grep/findstr), не полагайтесь на паттерны классического Netcode/Mirror!
* **CSP (`Simulate` / `IPredictedData`):** Используется для предсказания самого игрока (движение, прыжки, инвентарь). **Создавать и удалять объекты в CSP МОЖНО**, но только через специальные методы `predictionManager.hierarchy.Create()` и `predictionManager.hierarchy.Delete()`. Они поддерживают откаты. Чтобы статичный объект можно было удалить через `hierarchy.Delete()`, он обязан наследовать `PredictedIdentity` (например, `StatelessPredictedIdentity`), а не `NetworkBehaviour`.
* **`[ServerRpc]`:** Используется для сложных взаимодействий с миром, которые не требуют мгновенного локального предсказания (нажатие кнопок, спавн мобов). Требует стандартного `NetworkBehaviour`.
* **`SyncVar` / `NetworkTransform`:** Используется для **ОТОБРАЖЕНИЯ СОСТОЯНИЯ** (здоровье врага, открыта ли дверь). Сервер меняет переменную, клиенты пассивно читают её. Требует стандартного `NetworkBehaviour`.

## Архитектура и Логика

### 1. State Machine (Конечный автомат) персонажа
Контроллер игрока управляется строгим State Machine. Запрещено писать спагетти-код из `if/else` в `Update`. Основные состояния:
* `MoveState`: Дефолтное состояние. `CharacterController` (Этап 1) или `PredictedRigidbody` (Этап 2) управляет движением. Игрок может бегать и прыгать.
* `ScanState`: Взаимодействие с эталонным предметом. Блокировка движения, `ServerRpc` для записи ID предмета в «память» игрока. Сервер валидирует, что предмет не занят другим игроком.
* `TransformState`: Игрок превратился в предмет. Базовое управление отключено, физика переключена на dynamic Rigidbody формы. Игрок-форма существует как свободный физический объект.
* `AttachedState`: Игрок-форма присоединён к составному объекту (механизму/машине). Собственная физика отключена, позиция определяется слотом механизма. Инпут игрока перенаправляется в механизм (см. раздел «Составные объекты»).
* `RevertState` (опционально): Обратная трансформация с плавным переходом.

На **Этапе 2** состояния мигрируют на `PredictedStateNode<INPUT, STATE>` / `PredictedStateNode<STATE>`, логика перехода — через `PredictedStateMachine.SetState()`.

### 2. Физика трансформации (Kinematic ↔ Dynamic)
Переход между гуманоидом и физическим предметом — ключевой технический вызов.

* **Взаимоисключающие компоненты:** `CharacterController` и `Rigidbody` (dynamic) **не могут быть активны одновременно** на одном GameObject. При трансформации:
  - `CharacterController` отключается (`enabled = false`).
  - `Rigidbody` переводится из `isKinematic = true` в `isKinematic = false`.
  - При обратной трансформации — обратный порядок.
* **Подмена коллайдеров:** Капсульный коллайдер гуманоида выключается, включается коллайдер формы (Box, Sphere, Mesh) с настроенным `PhysicsMaterial` (Bounciness, Friction).
* **Сетевая синхронизация:** Команда на трансформацию идёт через `ServerRpc → ObserversRpc`. Все клиенты одновременно переключают компоненты, обновляют массу и `centerOfMass`. Для предотвращения «выстреливания» коллайдеров — принудительно задавать позицию при смене формы.
* **Game Feel:** Трансформация визуально мгновенна для инициатора, но сопровождается VFX-телеграфом (предупреждение для других игроков) и локальными эффектами (звук, партиклы). Эффекты привязаны к `ObserversRpc`, а не к локальному вызову.

### 3. «Память» форм
* У персонажа ограниченное число слотов для скопированных форм.
* Данные о скопированных формах хранятся в `SyncList<FormId>` (Server Auth), чтобы:
  - Сервер мог валидировать легальность трансформации.
  - При переподключении клиент автоматически получал актуальный набор форм.
  - Все клиенты знали, какие формы доступны каждому игроку (для UI индикаторов).

### 4. Жизненный цикл эталонных предметов
* Эталонные предметы — сетевые объекты с `NetworkIdentity`, размещённые на уровне.
* При сканировании: сервер записывает ID формы в `SyncList` игрока и вызывает `Destroy()` на эталонном предмете.
* Race condition (два игрока сканируют одновременно): сервер обрабатывает `ServerRpc` последовательно; второй вызов проваливает валидацию (предмет уже уничтожен).

### 5. Составные объекты (Механизмы / Машины)

Ключевая механика игры — несколько игроков-форм могут объединяться в **составной объект** (механизм). Пример: машина, где один игрок — колесо (тяга), другой — руль (поворот).

#### Архитектурный паттерн: Server-Auth Mechanism + Slot Input

**Почему сервер-авторитетный:** У механизма нет одного владельца-игрока — его контролируют несколько игроков одновременно. Поэтому физика механизма симулируется **на хосте** (`NetworkRigidbody` с `Owner Auth = false`, без owner). Каждый игрок-слот отправляет свой инпут на хост через `ServerRpc`, хост агрегирует все входы и применяет физику.

#### Компоненты механизма

```
MechanismController : NetworkBehaviour
├── Rigidbody (isKinematic, пока не собран)
├── NetworkRigidbody (Owner Auth = false)
│
├── SyncVar<bool> isAssembled         // механизм готов к движению?
├── SyncDictionary<SlotType, PlayerID?> slots  // какой игрок в каком слоте
│
├── [ServerRpc(RequireOwnership = false)]
│   RequestAttach(SlotType slot)       // игрок просит занять слот
│
├── [ServerRpc(RequireOwnership = false)]
│   SubmitSlotInput(SlotType slot, SlotInput input)  // игрок шлёт инпут для своей роли
│
├── [ObserversRpc]
│   OnSlotChanged(SlotType, PlayerID?)  // уведомление всех о смене состава
│
└── Server-side FixedUpdate / OnTick:
    AggregateAndSimulate()
    ├── WheelSlot input → Rigidbody.AddForce (вперёд/назад)
    ├── SteeringSlot input → Rigidbody.AddTorque (поворот)
    └── (будущее: BoosterSlot, BrakeSlot, ...)
```

#### SlotType и расширяемость
* `SlotType` — enum, определяющий роль слота (`Wheel`, `Steering`, `Booster`, `Brake`, ...).
* Каждый слот принимает определённый `FormId`. Например, слот `Steering` принимает только форму «руль», слот `Wheel` — только «колесо».
* Механизм может иметь **условие сборки**: например, не двигается, пока не заполнены обязательные слоты (руль + хотя бы одно колесо).
* Количество и типы слотов настраиваются на префабе механизма — новые механизмы создаются без изменения кода.

#### Жизненный цикл взаимодействия
1. Игрок в `TransformState` (форма «колесо») подходит к механизму и видит свободный слот.
2. Игрок вызывает `RequestAttach(SlotType.Wheel)` → `ServerRpc`.
3. Хост валидирует: слот свободен? Форма игрока соответствует слоту? Игрок рядом?
4. Хост записывает `PlayerID` в `slots[SlotType.Wheel]`, вызывает `ObserversRpc` → все клиенты:
   - Визуально перемещают модель игрока-колеса в точку крепления слота.
   - Переводят игрока в `AttachedState`.
   - Отключают собственный `Rigidbody` / `NetworkRigidbody` игрока (позиция теперь определяется механизмом).
5. Игрок-колесо считывает инпут (вперёд/назад) и отправляет `SubmitSlotInput` → хост применяет `AddForce`.
6. При отсоединении: обратный процесс, игрок возвращается в `TransformState`.

#### Синхронизация позиций прикреплённых игроков
* Визуальная модель прикреплённого игрока следует за слотом механизма **локально** (child transform или offset от `NetworkRigidbody` механизма).
* Собственный `NetworkTransform` / `NetworkRigidbody` игрока **отключается** на время прикрепления — его положение определяется механизмом.
* При отключении — позиция берётся из точки крепления слота, `NetworkRigidbody` включается обратно.

#### Камера в AttachedState
* Камера переключается на отслеживание механизма (не конкретного слота), чтобы игрок видел общую картину.
* UI показывает: текущая роль, состав экипажа, подсказки управления для данной роли.

## Камера
* Third-person камера, следящая за персонажем.
* При трансформации камера переключается на отслеживание нового меша/формы.
* При присоединении к механизму — камера следит за механизмом целиком.
* Камера — **чисто локальный объект**, не синхронизируется по сети.

## Дополнительные заметки для ИИ
* **Не использовать** `Time.deltaTime` / `Time.time` / `UnityEngine.Random` внутри predicted-кода (Этап 2). Вместо них — `delta` из callback, `PredictedTime`, `PredictedRandom`.
* **Не использовать** `FixedUpdate` для predicted-физики. Физика тикает через `PredictionManager`.
* **VFX/звуки** в predicted-коде — только через `PredictedEvent` или проверку `predictionManager.isVerifiedView`, чтобы избежать дублирования при replay.
* **`OnSpawned(bool asServer)`** вызывается дважды на хосте (один раз как сервер, один раз как клиент). Всегда учитывать параметр `asServer`.
* **Составные объекты** всегда Server Auth (Owner Auth = false), потому что ими управляют несколько игроков. `RequireOwnership = false` в `ServerRpc` обязателен для приёма инпута от не-владельцев.
